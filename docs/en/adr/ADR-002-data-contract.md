# ADR-002: Data contract between Python and the web

- **Status**: Accepted (reviewed and approved in issue C0-08)
- **Date**: 2026-11-12 (accepted on 2026-11-14)
- **Decided by**: the team, in a joint review of Python and web (2026-11-14)

## Context
Python (ephemerides and terrain) and the web work in parallel. If we do not agree on the format from the start, the first integration on Saturday will fail.

## Decision
- Python precalculates and writes **JSON** to `data/public/`; the web only reads. They communicate **only** through those files.
- **Columnar** format (parallel arrays) with `start_utc`, `step_s` and `count` for time. All files carry `schema_version`.
- Conventions: azimuth 0° = north, clockwise; elevation above the local horizon; degrees; UTC; topocentric frame; discs for the Sun and the Earth.
- **Visibility rule (confirmed)**: a body is visible if its upper edge is above the horizon (`elevation + radius > horizon(azimuth)`). The upper edge is chosen over the center and the full disc.
- JSON schemas in `data/schema/`, validated by `tests/test_contract.py`.
- The web starts with synthetic data generated by `scripts/make_synthetic_data.py`.

## Discarded alternatives
- List of objects per sample: heavier and slower files to read.
- CSV: no nested structure or clear versioning.
- Live API: more pieces that can fail during the demo.

## Consequences
- Contract changes require an ADR and a notice to the team.
- Python and the web implement the same visibility rule and cross-check against `metrics.json`.
- Confirmed in the review: azimuth and elevation go together, 1-hour step (`step_s` = 3600) for ephemerides, flat horizon until there is relief, and nominal radii (Sun 0.25°, Earth 1.0°).
- Pending: variable angular radius per sample (v1.1).
