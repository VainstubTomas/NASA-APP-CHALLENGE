# 04. Git workflow: MiniGitFlow

Last update: 2026-11-13 · Status: accepted by the team

A GitFlow reduced to what is useful for a two-day hackathon. Goal: each person works on their own branch without blocking or breaking the others. It is a multidisciplinary team: everyone touches any area and the rules apply to everyone equally.

## Branches
| Branch | Purpose | Rules |
|---|---|---|
| `main` | What is shown and delivered. Always demoable | Protected (hook and GitHub rule). Only receives merges from `dev` at milestones |
| `dev` | Integration of everyone's work. It is the team's sandbox | No technical protection (no hook or GitHub rule). By convention, everything enters via PR |
| `feature/<n>-<slug>` | One issue, one branch (e.g. `feature/12-horizon-profile`) | Born from `dev`. Short-lived (under ~4 h). Not deleted after merging |
| `fix/<n>-<slug>` | Bug fix | Same as `feature` |

We do not use `release/*` or `hotfix/*`: the "release" is merging `dev` into `main` at a milestone, and if `main` breaks, the merge is reverted and fixed in a `fix/*`.

## Epics
An **epic** is a parent issue that groups all the issues of one **layer** (phase) of the MVP: there is one for each layer (0 to 5) and one for delivery. It represents a complete demo: the layer 2 epic, for example, is done when the real horizon is seen with the Sun and the Earth above it.
- **How it is recognized**: the title starts with `[EPICA]` (e.g. `[EPICA] Capa 2: horizonte real con el Sol y la Tierra encima`) and carries the label `tipo:epica` plus its layer's label.
- **What it contains**: the issues of its layer hang as **sub-issues** (a native GitHub feature). The epic shows progress (how many sub-issues are closed), and each issue shows which epic it belongs to.
- **How it is used**: an epic is **not taken or worked on directly**: it has no assignee, branch or PR. Work happens in its sub-issues, and the epic is closed when all of them are closed (or dropped when cutting scope) and the layer's demo works.
- **Where it comes from**: defined in `scripts/issues.json` (`epics`), and `scripts/create_issues.py` creates it along with its sub-issues. A new issue of a layer hangs from that layer's epic.
- See ADR-008.

## Board and dependencies
Board "Hackaton" (GitHub Projects #3). Columns: `Backlog` → `Todo` → `In progress` → `Code review` → `Done`, plus `Blocked`.
- Epics start in `Todo` and issues in `Backlog`. When a layer starts, its issues move to `Todo`.
- **Dependencies**: only real data dependencies (for example, there are no ephemerides without the Horizons download) are loaded as GitHub "blocked by" relationships, from `blocked_by` in `scripts/issues.json`. Each issue shows what blocks it, without freezing anyone: most of the web moves ahead with synthetic data.
- **`Blocked` column**: only for an issue you have already started and are stuck on (something is missing from someone else, a data point, an answer). Say in the issue what you are waiting for. It is not used to mark future phases.

## Work cycle
1. Take an issue from the board (never an epic) and assign it to yourself.
2. Create the branch from `dev`.
3. Work with small commits.
4. Pull the latest changes from `dev` before opening the PR.
5. Open the PR to `dev` with `Closes #n`.
6. Another person reviews (5 minutes): does it run, does it meet the issue, does it break anything?
7. Merge by **squash** (recommended: leaves one commit per issue; GitHub also allows merge commit and rebase, we do not block them). The branch is kept: during the hackathon it is useful to be able to go back to it.

## PR rules
- One PR per issue, short description (the template helps).
- The PR title follows the commit rule (see below, 10 words or more): if it is merged by squash, that title becomes the commit message and does not go through the `commit-msg` hook.
- 1 approval from any other team member.
- If you touch a folder another person is modifying, say so in the PR.
- A broken `dev` is everyone's priority.

## Commits
The only rule the hook validates is the **length**; the rest is team convention. This way the messages generated by the AI-powered IDE can be used.
- **Length (mandatory)**: the first line has 10 words or more. Say what changes and why, so the team understands it without opening the code.
- **Language (convention)**: English, even though the documentation is in Spanish. The hook does not check it.
- **Suggested format (not mandatory)**: `type(scope): description`, with types `feat`, `fix`, `docs`, `test` or `chore` and scopes such as `web`, `ephemeris`, `terrain`, `data`, `tests`, `docs`, `scripts`. If the IDE generates another style, it is accepted as long as the length is met.
- Automatic Git merges and reverts pass without validation.

Suggested example: `feat(web): add site and date selector to the main map screen of the app`.
Example the hook rejects: `feat: perfil de horizonte` (fewer than 10 words).

### Hooks
They live in `.githooks/` and are activated **once per clone**:
```bash
git config core.hooksPath .githooks
```
- `commit-msg`: validates that the first line has 10 words or more.
- `pre-commit`: blocks direct commits to `main`. `dev` is not blocked on purpose: it is the team's sandbox, and since everything enters via PR, it is not needed.
- `git commit --no-verify` skips them. Use it only in an emergency.
- Hooks do not see GitHub squash merges: that is why the **PR title** must also be descriptive, 10 words or more.

## What does NOT go into git
Elevation map (`*.tif`), Horizons cache (`data/raw/`), `.venv`, `node_modules`, notebooks. `.py` scripts instead of `.ipynb`. Heavy data is shared through the cloud. The JSON files in `data/public/` are versioned and generated by a script.

## Milestones: merges from `dev` to `main`
| When | What must be in `main` |
|---|---|
| Fri 13 (night) | Layer 0: repo, contract, test deploy, Sun validated against Horizons |
| Sat 14, before 14:30 | Minimal demo (layers 1 and 2 if possible) |
| Sat 14 / Sun 15, ~01:00 | Whatever works after the long session |
| Sun 15, 12:30 | Feature freeze. After that, only `fix/*` |
| Sun 15, 14:30 | Final version and upload to GitHub |

Before each merge to `main`: quick test of the deployed web. In the night session, when tired, whatever breaks breaks in `dev`, never in `main`.

## Automations
What GitHub does on its own when a PR is merged, and what is configured by hand. See ADR-010.

### Protection layers
| Where | What | How |
|---|---|---|
| Local (each clone) | `commit-msg` and `pre-commit` hooks | `.githooks/` (see "Hooks" above) |
| Server (GitHub) | Ruleset `main-protector` on the default branch (`main`) | PR with 1 approval, blocks force push, deletion and creation; all three merge methods allowed |
| Server (GitHub) | `post-merge` Action | Closes and labels the issues of the merged PR (see below) |
| GitHub Projects | Board workflows | Move the issue between columns and between projects |

The hooks and the ruleset complement each other: the hooks stop you before the push on your machine; the ruleset stops it on GitHub even if someone did not enable the hooks or used `--no-verify`. `dev` is left out of the ruleset on purpose (ADR-007).

### `post-merge` Action (`.github/workflows/post-merge.yml`)
**Purpose**: when a PR is merged, close the issue it resolves and add the label `ready:to:main`, without depending on the PR saying `Closes #n`. It is needed because `Closes #n` only closes the issue automatically if the PR targets the default branch (`main`), and our PRs target `dev`.

- **Trigger**: `pull_request` of type `closed`, only if `merged == true` (a PR closed without merging does nothing).
- **Permissions**: `issues: write` and `pull-requests: read`, with the workflow's own `GITHUB_TOKEN`.
- **How it finds the issues** (combines both routes and removes duplicates):
  1. The issues linked to the PR, via GraphQL `closingIssuesReferences` (covers `Closes #n` in the description and the manual link in the *Development* panel).
  2. The number in the branch name: `feature/<n>-...` or `fix/<n>-...`.
- **What it does with each one**: creates the label `ready:to:main` if it does not exist, adds it, and closes the issue as *completed*.
- **Chain effect**: when the issue closes, the board workflows move it to `Done` in "Hackaton" and add it to "Main migrate" (see below).
- **Where it has to be**: GitHub runs the workflow that is in the PR's **base** branch. Today it is in `dev`; not yet in `main`.

Cautions:
- If the branch carries the number of an issue that the PR does not fully resolve, the issue is closed anyway. We accept this because of the rule "one PR per issue"; if it happens, it is reopened by hand.
- Unverified: whether `closingIssuesReferences` returns data when the PR does not target the default branch. That is why the branch-name fallback exists: **respect the `feature/<n>-<slug>` format**.

### GitHub Projects boards and how they relate
The same issue can be in several projects at once: it is not duplicated, it is added to the other project.

| Project | Purpose | Columns (`Status`) | Other fields |
|---|---|---|---|
| **A: "Hackaton 🪐"** (Project #3) | Hackathon work | `Backlog`, `Todo`, `In progress`, `Blocked`, `Code review`, `Done` | `Priority` (P0 to P2), `Size` (XS to XL) |
| **B: "Main migrate 🚀"** (Project #4) | Tracking issues closed in `dev` that must reach `main` | `From dev`, `Agrupation`, `Migrated` | |

Expected flow:
1. The PR is merged into `dev` → the Action closes the issue and adds `ready:to:main`.
2. In A, the "Item closed" / "Auto-close issue" workflows move it to `Done`.
3. In B, "Auto-add to project" adds it (filter of the type `is:issue is:closed label:ready:to:main`; without a label in the filter, every closed issue enters).
4. In B, "Item added to project" leaves it in `From dev`.
5. When `dev` is merged into `main` at a milestone, they are moved by hand to `Agrupation` / `Migrated`.

Active workflows (confirmed via API): in both projects, *Auto-add sub-issues*, *Auto-add to project*, *Auto-close issue*, *Item added to project*, *Item closed* and *Pull request merged*. *Pull request linked to issue* is active in A and disabled in B.

Known problem: some issues fell straight into `Migrated` in B (the last state). Probable cause: "Item added to project" or "Item closed" in B set to `Status: Migrated`. Fix:
- In B, `Workflows > Item added to project > Set Status: From dev`.
- In B, disable "Item closed" or change its status.
- Issues that already fell into `Migrated` are moved by hand to `From dev`.

Limits:
- Board workflows can only be edited from the GitHub web interface (they cannot be read or changed via API).
- The free plan limits the number of *auto-add* workflows.
- The *Auto-add to project* filter in B must use the same label the Action sets (`ready:to:main`).

## Initial repo setup (one time only)
On GitHub, `Settings > Branches > Add branch ruleset` for `main` (`dev` is left unprotected on purpose, see ADR-007):
- Require a pull request before merging, with 1 approval.
- Block force pushes.
- In the ruleset, leave the three merge methods allowed (no restrictions). Squash is recommended, but not forced.
- Leave "Automatically delete head branches" disabled: merged branches are kept on purpose.
Then run `scripts/create_labels.sh` and `scripts/create_issues.py` (they need `gh auth login` with the `project` scope: `gh auth refresh -s project`). The script creates the epics, the issues as sub-issues of their epic, and adds them to the "Hackaton" board (Project #3): epics in the `Todo` column and issues in `Backlog`.

### For each clone (each team member)
- `git config core.hooksPath .githooks` to activate the commit hooks.

## Command cheat sheet
```bash
git clone https://github.com/VainstubTomas/NASA-APP-CHALLENGE.git
git switch dev && git pull origin dev
git switch -c feature/12-horizon-profile        # create branch from dev
git add <files> && git commit -m "feat(terrain): add horizon profile computation for a single site and date"
git fetch origin && git merge origin/dev     # bring in the latest from dev
git push -u origin feature/12-horizon-profile
gh pr create --base dev                      # or from the GitHub web
```
If something goes wrong, do not delete anything: ask someone who already uses Git for help. With Claude CLI you have `/start-issue <n>` and `/ready-for-pr`.
